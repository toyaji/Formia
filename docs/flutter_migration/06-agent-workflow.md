# 06 — Opus(설계) / Sonnet(구현) 분업 프로토콜

토큰 효율을 위해 **큰 그림·설계 결정은 Opus, 실제 코드 구현은 Sonnet**이 맡는다. 이 문서는 그 경계와 지시 방법을 규정한다.

## 1. 역할 경계

| 역할 | 담당 | 산출물 |
| --- | --- | --- |
| **Opus (설계자)** | 아키텍처 결정, 문서(00~06) 작성/갱신, Phase 분해, 애매한 설계 판단, 코드 리뷰 게이트 | 설계 문서, 작업 지시(task brief), 승인/반려 |
| **Sonnet (구현자)** | 문서에 근거한 코드 작성, 테스트 작성, 로컬 실행/디버그, 좁은 범위 리팩터 | 코드 PR, 테스트, 실행 결과 보고 |

**원칙**: Sonnet은 **아키텍처를 발명하지 않는다.** 문서에 답이 없으면 구현을 멈추고 Opus에 질의한다.

## 2. 작업 단위(Task Brief) 템플릿

Opus가 Sonnet에게 넘길 때 항상 아래 형식으로 지시한다(하나의 Phase를 여러 brief로 쪼갠다).

```
### Task: <Phase N.x 제목>
- 목표: <한 문장>
- 근거 문서: docs/flutter_migration/<파일>#<섹션>  (읽을 것만 명시)
- 범위(파일/패키지): <건드릴 경로>
- 하지 말 것: <범위 밖·손대면 안 되는 것>
- 완료 기준(DoD): <검증 가능한 조건 + 테스트>
- 검증 방법: <melos run test / 특정 명령 / 실행 확인>
```

## 3. 실행 규칙 (Sonnet)
1. **문서 우선**: 지시된 근거 문서 섹션만 읽는다. 전체 문서 남독 금지(토큰 절약).
2. **작은 커밋**: 기능 단위로. 단, `CLAUDE.md` 규칙대로 **사용자가 명시 요청 전엔 커밋/푸시하지 않는다**(로컬 유지).
3. **테스트 동반**: 로직/도메인 코드는 테스트 없이는 완료로 보지 않는다(특히 `form_factor`).
4. **의존 규칙 준수**: 00 §ADR-6의 패키지 경계 위반 금지(예: UI에서 `supabase` 직접 import).
5. **막히면 질의**: 문서에 없는 설계 결정이 필요하면 코드로 추측하지 말고 Opus에 올린다.
6. **범위 고정**: brief의 "하지 말 것"을 넘지 않는다. 눈에 띄는 딴 문제는 별도로 보고만.

## 4. 리뷰 게이트 (Opus)
각 Phase 종료 시 Opus가 확인:
- DoD/테스트 충족?
- God-Store화(한 provider가 여러 관심사) 재발 없음?
- 문서와 코드 불일치(문서에 없는 패턴, 코드에 없는 문서) 없음? → 있으면 문서 갱신 또는 코드 수정.
- 패키지 의존 방향 위반 없음?

## 5. 권장 실행 형태
- Sonnet 작업은 별도 세션/서브에이전트로 구동하되 **모델을 Sonnet으로 지정**(비용 절감). 이 저장소에서는 사용자가 Sonnet 세션을 열거나, Opus가 `Agent` 도구로 구현 에이전트를 스폰할 때 `model: sonnet`을 지정.
- Phase 순서 준수: **1(도메인) → 2(백엔드) → 3(데이터) → 4/5(에디터) → 6(공개폼) → 7(컷오버)**. 도메인(`form_factor`)이 모든 것의 기반이므로 먼저 안정화.

## 6. "완료" 정의 (전 Phase 공통)
- [ ] DoD 항목 전부 충족
- [ ] `melos run analyze` 경고 0
- [ ] `melos run test` 통과(해당 패키지)
- [ ] 문서와 불일치 없음(신규 결정은 문서에 반영)
- [ ] 패키지 경계·God-Store 금지 원칙 준수
